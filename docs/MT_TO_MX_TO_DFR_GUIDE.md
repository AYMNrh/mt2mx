# MT → MX → DFR Guide

## 1. What this package does

This package answers three linked questions:

1. **What information exists in each MT message?**
2. **Where could that information go in the target MX message?**
3. **Where does the selected MX path land in the existing DFR model?**

It covers MT103, MT202, MT202 COV, MT910, and MT920. It is designed for traceable review: every source occurrence is accounted for, every proposed MX path is schema-checked, and every failed DFR join stays visible.

| MT | Target MX | Intended business meaning |

| MT910 | `camt.054.001.08` | Credit notification |
| MT920 | `camt.060.001.05` | Account-reporting request |

The target family choice does not prove that every field translation is valid for a particular network/profile/date. Those conditions require the applicable usage guidelines.

## 4. Evidence hierarchy

From strongest to weakest:

1. **Applicable SWIFT Translation Library and CBPR+ Usage Guideline** — not available; blocking approval.
2. **Official MT November 2025 Message Reference Guides** — primary source for MT occurrences, options, formats, presence, and network rules.
3. **Official/MyStandards ISO 20022 Message Definition Reports** — primary source for target message structure and meaning.
4. **PMPG cover-payment guidance** — supporting evidence for MT202 COV party semantics.
5. **Exact target XSD copies** — structural corroboration for XML paths, types, choices, and cardinalities. They are kept private and hash-registered.
6. **Open-source converters** — corroboration only; never used as authoritative approval.
7. **Derived semantic reasoning** — explicitly grade C/D and requires review.

## 5. Source registration and publication controls

`sources/source_manifest.csv` records:

- source identifier and authority;
- title/version/scope;
- filename, page count or row count;
- byte size and SHA-256;
- extraction and review status;
- distribution restriction;
- missing blocking artifacts.

Source PDFs, full extracted text, and XSD files are excluded by `.gitignore`. The public package contains only hashes and concise derived facts. This prevents accidental redistribution while preserving evidence identity.

## 6. MT extraction

The parser reads each numbered `Field N. Field TAG: Name` section and reconciles it to the message format table. Public output includes only:

- message and occurrence number;
- tag and field name;
- mandatory/optional status;
- sequence;
- options and format pattern;
- source PDF page index.

It does **not** publish definitions, usage-rule prose, or the full PDF text.

Observed counts:

- MT103: 23 occurrences, 6 mandatory and 17 optional;
- MT202: 11 occurrences, 4 mandatory and 7 optional;
- MT202 COV: 19 occurrences, 8 mandatory and 11 optional across sequences A/B;
- MT910: 9 occurrences, 4 mandatory and 5 optional;
- MT920: 5 occurrences, 3 mandatory and 2 optional.

## 7. MX path extraction

The XSD parser expands the XML type graph from `Document` and records:

- exact path;
- XML tag;
- data type;
- minimum/maximum occurrence;
- choice-group membership;
- attributes such as `@Ccy`.

## 8. Mapping-rule statuses

Every crosswalk row has:

- mapping action;
- transformation summary;
- evidence grade;
- evidence source IDs;
- corroboration, if any;
- validation status and review reason.

Actions:

- `DIRECT_CANDIDATE`: direct semantic copy, still profile-dependent;
- `TRANSFORM`: split, normalize, or code-map the MT value;
- `CONDITIONAL_CANDIDATE`: target depends on option/code/context;
- `NO_DIRECT_EQUIVALENT`: no safe ISO `Document` target was asserted.

All non-empty targets are `REVIEW_REQUIRED_CBPR`. `MT103#10 / 51A` is the sole `DOCUMENTED_GAP`; it should be reviewed in Business Application Header/network context.

## 9. Important transformations

Examples—these are baseline candidates, not final SWIFT rules:

- MT `32A` splits into settlement date, amount, and currency attribute.
- MT `33B` splits into instructed amount and currency.
- MT `50a`/`59a` options split into party name/address/identifier and account.
- MT agent fields split into BIC, clearing member ID, name/address, and account according to option.
- MT `71A` candidates use `OUR→DEBT`, `BEN→CRED`, and `SHA→SHAR`.
- MT920 `34F` splits into floor-limit amount/currency plus debit/credit direction.
- MT920 `12` requires translating requested MT report types to the agreed camt.052/camt.053 profile and version.

The original MT value must be retained in any implementation for replay and audit.

## 10. MX → DFR joining

The existing DFR mapping uses newer message versions:

| Candidate MX | DFR mapping version |
|---|---|
| `pacs.008.001.08` | `pacs.008.001.14` |
| `pacs.009.001.08` | `pacs.009.001.13` |
| `camt.054.001.08` | `camt.054.001.14` |
| `camt.060.001.05` | not present |

Joining is strict:

- same normalized XML path;
- same XML tag;
- attributes such as `/@Ccy` join to the parent DFR XPath plus `source_xml_tag=@Ccy`;
- no fuzzy or leaf-name-only joins.

Result:

- 222 exact matches;
- one `camt.054` `.../Dbtr/Pty/Id/OrgId/AnyBIC` path is valid in the XSD but absent from DFR;
- ten `camt.060` candidate rows remain `DFR_MESSAGE_NOT_IN_SCOPE`;
- MT103 51A remains `NOT_APPLICABLE`.

## 11. Blocking decisions

Production approval requires:

1. Register the exact CBPR+ Usage Guideline publication/version/applicability date.
2. Register the applicable SWIFT Translation Library version.
3. Review every grade C/D rule and every MT option/code branch.
4. Confirm Business Application Header handling, especially MT103 field 51A.
5. Define time/offset policy for 13C/13D.
6. Define charge sequence/agent derivation for 71F/71G.
7. Add `camt.060` to DFR or approve a direct DFR extension.
8. Test with confidential real samples and reconcile source→target values with zero unexplained loss.
9. Obtain business/operations, payments SME, AML, and data-governance sign-off.

Until those gates are complete, the package supports analysis and review—not automated production translation.

## 12. Runtime translator

The candidate baseline is executable in `mt2mx.runtime` (`translate()`). Test state (regenerated by `scripts/run_review.py`):

- Six synthetic samples (MT103 basic, MT103 FX/structured, MT202, MT202 COV, MT910, MT920) all translate to **schema-valid XML** against the exact private XSDs.
- 61 field mappings exercised; 4 documented skips (71F/71G charge details need an agent MT cannot supply; see `outputs/translation_review.csv`); zero present-but-unmapped fields.
- Every synthesized value is schema-mandatory but absent from MT and is always surfaced in `result.warnings`:
  - `SttlmInf/SttlmMtd=CLRG` and header BIC fallbacks (pacs.008/009);
  - `Sts=BOOK` and proprietary `BkTxCd=M910` (camt.054 — the entry status and bank transaction code are mandatory in the schema);
  - `Sts=INFO`, `CdtDbtInd` derived from floor-limit direction, `AcctOwnr` from sender BIC (camt.060);
  - `CreDtTm` defaults to the value date at midnight.

These synthesized values are translation-policy decisions that require profile approval before production use; they are never silent.

## 13. Review workflow

1. Start with `outputs/review_queue.csv` or the `Review Queue` workbook sheet.
2. Open all rows for one MT occurrence in `MT to MX Crosswalk`.
3. Check the source PDF at `mt_source_pdf_page`.
4. Check the exact MX path/cardinality in `MX Target Inventory` and the official Message Definition Report.
5. Check the DFR result in `MX to DFR Lineage`.
6. Record approve/change/reject with reviewer, date, rationale, and cited guideline section in a controlled review system.
7. Convert an approved candidate into an implementation rule only through tested code review.

## 14. Verification commands

```bash
PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 uv run pytest -q
uv run python scripts/verify.py
```

A clean verification checks tests, 67-source coverage, XSD target validity, DFR status reconciliation, workbook structure, and absence of private source extensions from tracked files.
